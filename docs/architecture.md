# Architecture — Hayati

## 1. Stack & rationale

| Layer | Choice | Why |
|---|---|---|
| App | **Flutter** (stable channel), Dart | One codebase for Android-heavy TR + iOS-heavy GCC; first-class RTL; widget-test culture fits our TDD mandate |
| State | Riverpod (+ codegen) | Testable, compile-safe DI, scales from MVP to v2 |
| Backend | **Firebase**: Auth (Google/Apple/phone), Cloud Firestore, Cloud Functions (TypeScript), FCM, Remote Config, Crashlytics, App Check | Solo-founder ops budget ≈ zero; offline persistence built-in; Remote Config gives the regional feature flags the GCC strategy requires |
| Payments | **RevenueCat** | Cross-store entitlements, webhooks, experiments; industry default for this exact app category |
| Analytics | Mixpanel (product funnels) + Firebase Analytics (audiences) | Free tiers cover Year 1; funnel tooling for the three gates |
| AI | LLM via **Cloud Function proxy only** | API keys server-side; per-user rate limits; safety filter; model-swappable; cost caps enforceable |
| CI/CD | GitHub Actions + Fastlane | Matches `project-rules.md` (gh CLI, pipeline-green rule) |

Firestore region: **europe-west (multi-region EU)** — defensible latency for both Istanbul and Riyadh, and a conservative posture for KVKK/PDPL cross-border rules. Revisit if KSA data-residency guidance tightens; the repository pattern below keeps a migration survivable.

Feature-first, clean-ish architecture: `presentation → domain ← data`. Domain layer is pure Dart (no Flutter imports) — this is what makes the 90% domain coverage target in `test-suite.md` cheap.

**Firebase environments (M1.2):** two real Firebase projects map to the two Dart-entrypoint flavors — **`hayatiapp-dev`** / **`hayatiapp-prod`** (iOS bundle id `com.beyondkaira.hayati` since Session 037 — `com.hayati.app` proved squatted on Apple and was renamed, ADR-027; Android still `com.hayati.app`, its id decision deferred with the platform to M6.5; the planned `hayati-dev`/`hayati-prod` project ids were likewise unavailable). Options live as committed per-flavor Dart files (`app/lib/core/firebase/firebase_options_{dev,prod}.dart`, generated by `flutterfire configure`, FlutterFire Dart-only init — no `GoogleService-Info.plist`/`google-services.json` committed and no google-services Gradle plugin, deliberately: one Runner/one Android app serves both flavors, so platform config files can't be per-flavor; config files are not secrets, API keys get console-side restrictions). Google sign-in OAuth client ids are likewise per-flavor **runtime** config (`app/lib/core/firebase/google_sign_in_config.dart`: iOS `clientId` ≙ `GIDClientID`, Android web `serverClientId`), with both flavors' iOS `REVERSED_CLIENT_ID` URL schemes registered side by side in `Info.plist`. *Provisioning learnings (Session 004):* free-tier Firebase **Auth initialization and Google-provider enablement are console-only** — the Identity Toolkit Admin API rejects provider creation without an existing OAuth client and `identityPlatform:initializeAuth` is the billing-gated Identity Platform upgrade; everything else (API enablement, `flutterfire configure`, Firestore database creation at `eur3`, rules deploy) is scripted via `firebase-tools`/REST. Environment bindings (Firebase-backed `AuthRepository`, Firestore-backed `ProfileRepository`) are composed in the entrypoints via `runHayati(..., extraOverrides: [...])`; base providers throw when unoverridden (the `appConfigProvider` pattern). Emulators stay opt-in dart-defines (`USE_AUTH_EMULATOR`, `USE_FIRESTORE_EMULATOR`, and since M2.2 `USE_FUNCTIONS_EMULATOR` — wiring the `europe-west1` `FirebaseFunctions` instance, the same regional instance the pairing repository resolves; the Firestore emulator needs **Java 21+**, relevant to ci-debt #6); runtime verification path is `app/integration_test/`. Firebase iOS SDK 12 raised the iOS floor: deployment target pinned to **15.0** in the Runner pbxproj (iOS plugins integrate via **Swift Package Manager** — the Flutter 3.44 scaffold is SwiftPM-first and has no Podfile; adding one breaks the build, verified on CI in Session 003).

**Auth providers (M1.3).** Three providers reach Firebase through one uniform seam in `features/auth/data/`: a gateway per provider that yields a Firebase `AuthCredential` (or `null` when the user cancels), which `FirebaseAuthRepository` exchanges via `signInWithCredential` inside its `_guarded` boundary. This shape exists because `signInWithCredential` forwards the credential unvalidated, so the Auth emulator accepts an *unsigned* JSON `id_token` — which is what makes every provider testable without a real account ([ADR-008](adr/008-apple-signin-via-credential-seam.md)). **Apple** uses `sign_in_with_apple` + `AppleAuthProvider.credentialWithIDToken` (never `signInWithProvider`, which surfaces no credential and therefore cannot be faked or emulated); the nonce is a two-value protocol — SHA-256 hex to Apple, plain `rawNonce` to Firebase. **Phone** is the one flow with a user-input gap, so it cannot be a single atomic call: `PhoneAuthGateway` adapts `verifyPhoneNumber`'s four callbacks into one `Completer` (guarded against double-completion — `verificationFailed`/`codeAutoRetrievalTimeout` can fire *after* `codeSent`, and the returned Future can reject independently), and a screen-scoped `PhoneSignInController` drives enter-number → code-sent → confirm. That controller **never writes the global `AuthState`**: the terminal `AuthSignedIn` arrives on the `authStateChanges` stream while `AuthController` is idle, preserving its manual-op precedence contract. On iOS `verificationCompleted` never fires (Android-only), so a code-entry UI is mandatory; on Android it fires *instead of* `codeSent` under instant verification, which would hang the send forever — the gateway therefore fails loudly there until real Android support lands (issue #13, M6.5). Emulator-side, phone codes are minted randomly per request and read back over the emulator's REST endpoint — **under the project the emulator was booted with (`demo-hayati`), not the app's `FirebaseOptions.projectId`** (the Auth emulator resolves every SDK request to its single `--project`; querying `hayatiapp-dev` returns an empty list, verified 2026-07-09).

**Crashlytics & App Check (M1.3).** Both are activated **only from the flavor entrypoints**, after `initializeFirebase` — never inside it, and never from `HayatiApp` — because `FirebaseAppCheck.activate()` and `FirebaseCrashlytics.instance` each drive a platform channel that throws in the plain `flutter test` VM, where the bootstrap and widget trees are unit-tested. Crash reporting crosses into the app behind a `CrashReporter` interface taking only framework types (`core/observability/`); exactly one file imports `firebase_crashlytics`, and `runHayati(..., crashReporter:)` installs `FlutterError.onError` + `PlatformDispatcher.onError` hooks only when a reporter is supplied, so tests stay channel-free. **Per-flavor collection policy: dev OFF (noise), prod ON**, applied at boot via the runtime `setCrashlyticsCollectionEnabled` API (it persists across launches and overrides plist defaults, so a device that switched flavors self-corrects). **App Check posture:** dev activates the *debug* provider, prod declares *App Attest* (always available at the min iOS 15.0 floor); activation is skipped entirely under `kUseAuthEmulator` so the integration leg stays hermetic. **Enforcement must stay OFF in both consoles until on-device attestation is verified** — enabling it early would lock the founder couple out of Auth/Firestore. Sign in with Apple adds `app/ios/Runner/Runner.entitlements` (`com.apple.developer.applesignin`), wired via `CODE_SIGN_ENTITLEMENTS` in the three Runner build configs; entitlements are consumed at codesign time, so CI's `--no-codesign` build is unaffected. *Deferred loudly to the on-device/Mac slice (nothing silent, rule #9):* App Attest entitlement + console app registration, per-device App Check debug-token registration, the `FirebaseCrashlyticsCollectionEnabled=false` Info.plist baseline that would close dev's first-launch pre-Dart collection window, dSYM upload for prod symbolication (the CocoaPods podspec adds it; SwiftPM does not), and real-device verification that Apple's first-authorization full name reaches `displayName`. **Crash-free posture audit (M6.3, ADR-022 D6 — audited, not rebuilt):** the mechanism above is confirmed live and correct (prod ON at boot, error hooks installed via `runHayati`, the M5.2 no-content rule keeping payloads clean); what the PRD §10 crash-free ≥99.5% gate still needs is exactly the already-recorded set — dSYM upload (item 4), a deployed prod app to report from (item 2), and Gate-2 funnel instrumentation (mvp item 11). Boot-stage timing is now observable via `BootTrace` (debug-only Timeline marks in both entrypoints, stage names only — release builds pay nothing), and the pre-frame await set is pinned by the mutation-checked entrypoint source sentinel (ADR-022 D1/D2: the tz-DB parse moved post-frame; App Check ∥ Crashlytics and prefs ∥ Keychain-snapshot overlap via `Future.wait`; `configureIfKeyed` deliberately stays — the warm-boot identity-sync trap is documented at the call site).

**Security rules invariants (tested against emulator):** a user reads/writes only their own couple's docs; partner's answer for today is unreadable until requester's answer exists (mutual-reveal enforced server-side, not just UI); invites expire; entitlement docs are function-write-only. *Shipped so far (M2.1 → M3.3, `firestore.rules`):* `users/{uid}` self-only with granular ops — `createdAt` **rules-enforced** create-once (`== request.time` at create, frozen on update — the M1.2 client transaction shape passes unchanged), client delete denied (hard delete is the M6 cascade Function), and since M2.3 **`coupleId` frozen against clients** (create may not include it, update may not set/change/delete it — `get('coupleId', null)` compared symmetrically so the app's merge writes pass; the field is authorization-meaningful, granting `couples/` access via `memberUids`, and is written only by the join Function); since M2.4 **`users/{uid}/soloAnswers/{dayKey}` self-only with a frozen field surface** — `hasOnly([questionId, text, answeredAt])`, bounded non-empty text (≤2000), `answeredAt == request.time` (a client clock can never forge the answer time; same server-stamp discipline as `createdAt`), same-day overwrites allowed by design (the answer stays editable all day), client delete denied (the M6 cascade owns removal); `couples/{coupleId}` member-only read/update with `memberUids` frozen (couple create/delete is exclusively the M2.3 transactional-join Function / M6 cascade) — **and since M3.3 `timezone` + `createdAt` frozen too** (the stored zone is dayKey-load-bearing on BOTH sides: the rollover buckets by it and the app keys the day by it, so a member rewriting it to junk would brick the couple's loop; zone changes move behind a future settings Function, mutation-tested both freezes); since M3.2 **`couples/{cid}/days/{dayKey}` member-only read with ALL client writes denied** (function-only via admin SDK — the rollover is the sole writer; membership needs a `get()` of the parent couple because the day doc carries no uids, and an orphaned day under a deleted couple fails closed), mutation-tested both ways (membership guard weakened → non-member read succeeds; the write-deny swapped for authed-allow → client write succeeds); since M3.3 **`couples/{cid}/days/{dayKey}/answers/{authorUid}` carries the mutual-reveal invariant server-side**: create/update self-only AND member-of-couple (parent `get()`), frozen `hasOnly([questionId, text, answeredAt])` surface with non-empty text ≤2000 and `answeredAt == request.time`, `questionId` pinned by `get()` to the parent day doc's assigned question (no day doc → no answers, fails closed), **read = member AND (own doc OR `exists()` of the requester's own answer)** — the partner's answer is unreadable before the requester answers, a whole-collection `list` flips with the same branch (denied pre-answer, allowed post-reveal), updates are denied once BOTH answers exist (reveal freezes the pair — no rewrite-after-reading), delete denied (the reveal gate is one-way; removal is the M6 cascade). Proven by 21 new rules cases plus **12 mutation tests** (reveal `exists()` gate dropped → pre-answer partner read succeeds; read/write membership guards dropped → non-member access succeeds; `isSelf` weakened → partner-doc writes succeed; `hasOnly`/server-stamp/questionId-pin/non-empty-text dropped → each junk write succeeds; both-answered freeze dropped → post-reveal rewrite succeeds; delete allowed → post-reveal retraction succeeds; `timezone`/`createdAt` freezes dropped → member rewrites succeed); since M3.4 **`couples.streak` frozen too** (same symmetric `get('streak', null)` comparison as `users.coupleId` because the field is absent pre-first-mutual-day — a member can neither introduce, change, nor delete it; the answerReveal trigger is its sole writer, mutation-tested like the other freezes); `invites/{code}` **no client access at all** — writes come from `createInvite`/`joinInvite` (admin SDK) and the invitee-facing read is the M2.2 zero-auth preview Function, so codes can't be enumerated client-side; since M4.1 **`subscriptions/{coupleId}` member-only read with ALL client writes denied** (the doc id IS the coupleId, so membership needs a `get()` of that couple — the M3.2 `days` pattern; an orphaned mirror under a deleted couple fails closed; the `revenueCatWebhook` Function is the sole writer, delete belongs to the M6 cascade), mutation-tested both ways (write-deny swapped for authed-allow → member client write succeeds; membership guard weakened → non-member read succeeds); since Session 023 (ADR-023) **`users.consent` is SERVER-OWNED** (create-forbid + update-freeze, both mutation-tested; the `recordConsent` callable is the sole writer and stamps its own version) **and the special-category answer writes carry a consent predicate** — soloAnswers + couple-answers create/update require `get(users/$(request.auth.uid)).data.get('consent', null) != null` (presence-only, version-blind: rules cannot read the version constants, the app gate owns version currency — the bound is recorded, parity is not claimed), mutation-tested on both surfaces (predicate weakened → a consentless write succeeds); default-deny for everything else. Every invariant is proven by `functions/test/emulator/firestore-rules.test.ts`, including **mutation tests** that load a weakened copy of the rules and show the denial disappears — the suite goes red if a protecting clause is commented out. Client wire mapping for `users/{uid}` lives in `app/lib/features/profile/data/profile_dto.dart` — enum `name`s are the wire values and renaming one is a data migration.

**Invite issuing (M2.1, `functions/`).** The repo's first Cloud Functions code: TypeScript strict on **firebase-functions v7 / Node 22** (bumped from 20 in S043/ADR-030 — `nodejs20` is **decommissioned 2026-10-30**; `nodejs22` and `nodejs24` share a 2028-10-31 decommission date, so 22 was chosen as the conservative option with no runway cost). **firebase-admin is `^14`** (S044/ADR-031, closing #107 — the `^13` pin existed only because *v14 requires Node ≥22*, a constraint ADR-030 lifted). The honest headline of that bump is **`@google-cloud/firestore` v7 → v8**, the client every Firestore call runs through, so it was verified against the two most exposed suites deliberately: ADR-019's resumable cascade on the real emulator (58) and ADR-013/015's entitlement LWW convergence property (109). `firebase-functions` v7 remains deliberately un-bundled, vitest + v8 coverage with the `test-suite.md` §3 gate (target 85%, **hard fail <80%** via thresholds), eslint flat config. `createInvite` is an **onCall v2 callable in `europe-west1`** (closest single region to both Istanbul and Riyadh, consistent with eur3; the M2.2 client must construct its callable with this region): auth required (guarding `auth.uid` itself, not just presence — the functions emulator skips real token verification, and it's free defense-in-depth), App Check **token plumbed but enforcement OFF** (`enforceAppCheck: false` until on-device attestation is verified, M1.3 posture; token presence is logged to observe attestation coverage pre-enforcement). Codes are 8 chars from a 31-char unambiguous alphabet (A–Z + 2–9 minus O/I/L — survives being read aloud or retyped from WhatsApp; 31⁸ ≈ 8.5e11). **Re-issue policy: one active invite per creator** — a pending, unexpired invite is returned as-is (idempotent; re-opening the share flow never invalidates the code the partner already has), stale pendings are lazily marked `expired` and replaced; invites never accumulate. Everything runs in one Firestore transaction (pending-invite query + collision probes are reads-before-writes; `tx.create` fails if the code doc appeared meanwhile), so concurrent calls serialize and the loser returns the winner's code — proven against the emulator. Emulator wiring gotchas that cost real time, recorded once: the functions emulator **never compiles TS** (build `lib/` before `emulators:exec`), injects **no functions-host env var** into the exec child (tests derive `http://127.0.0.1:5001/<project>/<region>/<name>` from the pinned port), firebase-tools finds Java **via PATH only** (JAVA_HOME is never read; the firestore emulator needs Java 21+), and the functions emulator serves functions **only under its `--project` id** — a Flutter app initialized with a real flavor's `FirebaseOptions` builds the emulated callable URL from *its* `projectId` and 404s (`NOT FOUND`), because unlike the auth/firestore emulators (which resolve any project id) the functions emulator routes by URL path; emulator-backed integration tests must therefore initialize their default app with `demo-hayati` options (found the hard way on the first `integration-emulator` run of M2.2, fixed in PR #23).

**Invite preview (M2.2, `functions/`).** `invitePreview` is an **onRequest v2 HTTP endpoint in `europe-west1`**, zero-auth by design — the invitee has no account yet, so a callable's auth/App Check envelope would be dead weight (the onCall-vs-onRequest split was pre-decided in Session 007, not re-contested). Contract: `GET ?code=` → HTTP 200 `{status: 'valid'|'expired'|'unknown', creatorDisplayName?}`. **The response surface is exactly those fields** — never `creatorUid`, other invites, or (once M3 content exists) answer content; the suite's field-surface tests assert `Object.keys(body)` per case, so an accidentally added field turns CI red. This is where the §4 invariant "preview never leaks answer content" starts; the projection lives in one typed helper so the M3 growth (`questionText` + locked indicator) stays an explicit, reviewed surface change. Lookups return a **uniform 200/`{status}` shape for all three outcomes** (no enumeration oracle beyond validity — `expired` vs `unknown` only distinguishes a code you already hold), and malformed codes (checked against the alphabet/length imported from `invite-code.ts`) short-circuit to `unknown` without a Firestore read. The endpoint is strictly **read-only**: a stale pending is *reported* `expired` by comparing `expiresAt`, never written — a zero-auth path must not amplify writes; lazy expiry stays `createInvite`'s job (proven by a test that previews a stale invite and re-reads the doc). `creatorDisplayName` comes from the creator's **Auth record** (`users/{uid}` stores no display name) and is omitted — still `valid` — on any lookup failure. Logs avoid becoming an oracle: a 3-char code prefix is logged, never validity-plus-full-code. **Rate-limiting decision (recorded per resume-prompt):** a best-effort **in-memory fixed-window per-IP limiter (30 req/min → 429)** guards the endpoint — per-instance and reset on cold start, so it is an abuse damper, not a guarantee; the real anti-enumeration defense is the 31⁸ (~8.5e11) code space plus function-only reads. Infrastructure-grade limiting (Cloud Armor / API Gateway) is deliberately out of scope until a public launch surface exists. No CORS: the native app is the only consumer; a future web preview adds it deliberately.

**Transactional join (M2.3, `functions/`).** `joinInvite` is an **onCall v2 callable in `europe-west1`** (auth required with the same uid-not-just-presence guard as `createInvite`; App Check plumbed, enforcement OFF — M1.3 posture). Request `{code, timezone?}` → `{coupleId}`. Everything happens in **one Firestore transaction** (all reads before writes): read `invites/{code}` → both `users` docs, check in a deliberate order (existence → terminal-state → self-join → profile-missing → already-paired), then create `couples/{auto-id}` (`memberUids: [creatorUid, joinerUid]` — creator first, frozen), set `coupleId` on both `users` docs, and stamp the invite `{status: 'joined', coupleId, joinerUid, joinedAt}`. **Typed error surface (frozen wire contract the app maps on):** `not-found`/`{reason:'unknown'}` for absent or malformed codes (malformed short-circuits without a read — no enumeration oracle); `failed-precondition` with `reason` `'expired'` (status or clock or malformed doc), `'consumed'` (status `'joined'` — the race loser's answer), `'self-join'`, `'already-paired'` (either side has `users/{uid}.coupleId`), `'profile-missing'` (either `users` doc absent — the app flow guarantees profile-before-join; this is defense-in-depth). **Race semantics are the acceptance criterion:** two concurrent joins serialize on the invite doc; the admin SDK retries the ABORTED loser, whose retry re-reads the invite — now `'joined'` — and throws `consumed`; typed rejections always come from re-read state, never from inspecting commit conflicts (proven at service AND callable level against the emulator, exactly one couple per code). **Couple `timezone` source (documented decision):** the joiner MAY supply an IANA id, validated against `Intl.supportedValuesOf('timeZone')`; absent/unrecognized falls back to `Europe/Istanbul` (founder-couple / TR soft-launch home zone). The app currently sends nothing — a reliable device IANA source needs a plugin, deferred to M3 where the rollover work makes it load-bearing. `createInvite` gained the symmetric guard: an already-paired creator gets `failed-precondition`/`'already-paired'` instead of a fresh code, so re-issue after a join can never resurrect or replace a spent code (a `'joined'` invite also previews as the uniform `'expired'`).

**Solo mode (M2.4, app-side — no Functions footprint; full rationale in ADR-009).** The unpaired user's home shows the day-N solo reflection question with an answer entry and a **persistent invite nudge** on every settled state (honest better-together framing per `prd.md` F1). Content: three bundled JSON packs (`app/assets/content/solo_{tr,ar,en}.json`) shaped exactly like `content/schema/question-pack.schema.json` (register `neutral`, exactly 7 questions — enforced at load), selected by `profile.contentLanguage` and read through a `SoloQuestionPackRepository` seam with a loud pure mapper. **Since M3.1 the packs are authored under `content/packs/` and byte-synced into the bundle by the enforcing validator (ADR-010: CI check mode red on drift, `--sync` regenerates), and the model is the general one** — `QuestionPack`/`Question` (`register` carried, per-question `seasonalWindow` surfaced) loaded by packId through `AssetQuestionPackRepository`, the solo path a thin specialization (`solo_<locale>`, exactly-7 + locale checks) behind the unchanged seam; remote pack sync and register-aware resolution remain M3.2+. Day N anchors on `users/{uid}.createdAt` — surfaced to the client **READ-ONLY** exactly as `coupleId` was at M2.3 (the repository converts the wire `Timestamp` to `DateTime` at the boundary; `profileToMap` still never emits it) — and is a **local calendar-date distance** (`solo_day.dart`: date components only, so DST can't move a boundary; null/future anchors clamp to day 1; the wall clock enters via `soloClockProvider`, the app's single clock seam). **Day 8+ stops the cycle** — questions never repeat; the completed state makes the invite the primary action. Answers persist to `users/{uid}/soloAnswers/{yyyymmdd}` (dayKey = the same local calendar date; same-day saves overwrite — the answer stays editable all day) through a `SoloAnswersRepository` seam mirroring the profile repository's exception taxonomy. The share flow stays one tap away behind the nudge as a **pushed route** that pops itself when `coupleId` lands (partner joined while the user sat on it) or on sign-out — the gate underneath has already re-routed either way.

**Daily rollover (M3.2, `functions/` — full rationale in ADR-011).** `questionRollover` is the repo's first **scheduled Function** (`onSchedule` v2, `europe-west1`, `0 * * * *` UTC, explicit `timeoutSeconds`/`memory`): a **single hourly sweep** reads all couples, buckets them by their stored `timezone` (verbatim — never re-resolved through the join-time default, so corrupt state surfaces instead of masquerading as Istanbul), computes each bucket's **local calendar date once** (`rollover/day-key.ts`: `Intl.DateTimeFormat` `formatToParts` pinned to `gregory`/`latn` — DST-correct by construction, immune to locale calendar/digit drift), and **creates `days/{dayKey}` only if absent** (`create()`; an existing day doc is never reassigned, losing the race to an overlapping run is a benign no-op because selection is deterministic). Selection (`rollover/select-question.ts`, pure — a function of pack + history + **the dayKey being written**): **in-window seasonal UNSEEN-first**, else evergreen (first unseen in pack authoring order, then min-times-assigned recycle with pack-order tie-break after exhaustion), else recycle the in-window seasonal set, else throw. Seasonal windows landed with **ADR-026** (Session 037, closing ADR-011 D4's evergreen-only deferral and issue #29): a CLOSED four-value vocabulary (`ramadan` = the whole Hijri month 9, `eid_fitr` = Shawwāl 1–3, `eid_adha` = Dhū al-Ḥijjah 10–13, `new_year` = Dec 31 – Jan 1) resolved in `rollover/seasonal-window.ts` from ICU's Umm al-Qura calendar over UTC-noon of the dayKey — **the doc id, never the wall clock**, so two overlapping sweeps assigning the same day agree on the verdict. Two things there are load-bearing: the preference is for *unseen* seasonal questions only (always-preferring would loop a handful of Ramadan questions for thirty days while the curriculum sat idle), and the calendar is **guarded** — `Intl` does not throw for an unsupported calendar, it silently answers in **Gregorian**, which would fire ramadan every September forever, so the module verifies `resolvedOptions().calendar` and, failing it, reports every Hijri window CLOSED while the sweep logs it once and sets `RolloverSummary.seasonalCalendarUnavailable` (fail-closed on content, fail-open on availability). Umm al-Qura is calculated, so a window edge can differ by a day from local observance (Diyanet/sighting) — recorded, deliberately unpadded. The vocabulary is closed in **five** readers (schema `enum`, validator check, `validateSchemaAgreement` drift guard, the TS parser's narrowed type, the app DTO) because a free-string tag nothing recognises is a question that is never selected, silently, forever. History = a `questionId` projection over the couple's `days` subcollection (O(history) reads/assignment; the scale path — timezone-indexed sweep query + selection cursor — is documented in ADR-011 and deliberately not built). Packs are **bundled at build time** (`npm run build` = `tsc` + `scripts/bundle-packs.mjs` copying `content/packs/` → `lib/content/packs/`, byte-equality suite-enforced; the validator stays the single content gate, the strict TS parser at the consumption edge is defense-in-depth). **Error boundary:** per-couple problems (malformed `packConfig`, missing/corrupt timezone, unloadable pack, an all-seasonal pack *outside every window* — date-dependent since ADR-026) are logged skips counted in the run summary — never a failed run; the throw is reserved for systemic failures. The handler validates `event.scheduleTime` (nominal scheduled instant beats wall clock; garbage falls back loudly). The schedule *trigger* is emulator-untestable and was **deploy-verified in Session 040** (`firebase-schedule-questionRollover-europe-west1`, `0 * * * *` `Etc/UTC`, ENABLED on `hayatiapp-dev`; `answerReveal`'s Eventarc trigger ACTIVE with `RETRY_POLICY_RETRY` alongside it); everything else is proven in-process against the emulator — timezone buckets incl. DST boundaries, double-run idempotency at service AND handler level, the create race, and the per-couple skip taxonomy.

**Mutual reveal (M3.3, app + rules — the couple's daily loop closes).** The paired home (`features/daily_question/presentation/paired_home_screen.dart`, replacing the M2.3 placeholder behind the gate's `coupleId` route) walks the read path `couples/{coupleId}` (the app's first couple read — watch-only `CoupleRepository`; the doc carries the zone) → **`coupleDayKey(now, couples.timezone)`** (`couple_day.dart`, the Dart mirror of the rollover's `localDayKey` over `package:timezone`'s 10-year db, initialized at bootstrap and lazily as a net; parity with TS pinned byte-for-byte by the shared fixture `functions/test/fixtures/day-key-parity.json` incl. DST boundaries and sub-hour zones — NEVER `soloDayKey`/the device zone, ADR-011) → `days/{dayKey}` (watch-only; **null renders the honest no-day-yet state** and streams the assignment in live when the hourly sweep lands it — the client never predicts) → question text resolved from the bundled pack by `packId`+`questionId` (`AssetQuestionPackRepository`; an id the install doesn't bundle renders the "update the app" pack-lag state, typed via `UnknownQuestionPackException`). Answers write through `CoupleAnswersRepository.saveAnswer` (full-replace `set` of exactly the rules surface; `answeredAt` = `FieldValue.serverTimestamp()`). **The client half of the reveal invariant is `partnerSlotProvider`** (sealed `PartnerSlot`: locked → waiting → revealed | failure): it never attaches the partner-answer watch until the OWN answer is **server-acked** (`answeredAt != null` — a pending serverTimestamp local echo crosses as null), because a pre-answer listen would be denied and the SDK never retries a denied listen; a denial that slips through anyway (lost `exists()` race on a replica) maps to the locked state as defense-in-depth plus a bounded 3× re-subscribe (1s/2s/4s — the ONE narrow retry in the couple providers; everything else keeps the no-retry philosophy: corrupt state hammers nobody). Both-answered is the revealed state: the entry collapses to a read-only own-answer card (rules have frozen both docs). The screen recomputes the dayKey per build from `soloClockProvider` and on app-resume (`WidgetsBindingObserver` — the dominant path back after a couple's midnight; still no timer, ADR-009 precedent). A corrupt stored zone (`LocationNotFoundException`) renders an honest error view, never a guessed date. Couple questions come from the `solo_tr` placeholder bank until W9 (ADR-011) — the founders will recognize their solo questions; accepted for dogfooding.

**Data rights (M6.2, `functions/src/data-rights/` — full rationale in ADR-019).** The promise every rules doc-comment carried since M2 ("delete = the M6 cascade Function") is now a shipped callable, and not one client rule was loosened for it. **`deleteAccount`** (onCall, `europe-west1`, `timeoutSeconds: 540`, requires the app-sent wire literal `confirm: 'DELETE'`): one idempotent, resumable cascade — resolve-and-record **as one transaction** into the `deletions/{uid}` cursor (AUTHORITATIVE on every re-drive); ONE detach transaction (delete `couples/{cid}` + clear both members' `coupleId` + stamp the survivor's `coupleEnded`, with a re-pair guard so a re-driven cascade never dents B's new couple — **and seeding the PARTNER's cursor when absent**, because per-uid cursors alone could not carry the both-partners-concurrent claim: without the seed, a requester resolving after its partner's detach misread itself as unpaired and delegated its own couple-authored erasure to a possibly-abandoned cascade — the post-implementation review's serious find, fixed and mutation-checked); confirm-or-throw sweeps of the couple subtree, then the requester's own subtree, then invites (own-subtree FIRST so the deleted profile fail-closes `createInvite` before the invite sweep — closing the intra-cascade mint window); seed-cleanup + cursor removal; and LAST the idempotent `deleteUsers([uid])` (the plural — the singular throws on a re-driven, already-deleted uid), so any earlier failure leaves the caller authenticated and able to re-drive. Kill-after-every-step convergence, the A-and-B distinct-uid concurrency suite (incl. the abandonment case), and the live-evaluated re-pair guard are emulator-pinned. **`exportData`** (no premium gate — a data-subject right is not a feature tier) returns a versioned in-app JSON envelope (`formatVersion: 1`, epoch-ms time fields) of strictly the requester's own data: profile + Auth-record fields, solo answers, their OWN couple answers only (B's text never crosses, revealed or not — B-data-minimization over the two-subject object, ADR-019 D5), their own coach daily lane only (the ADR-016 D7 self-read invariant applied to export), the subscription summary + their own lane, and their invites with the counterpart uid scrubbed. **`updateNotificationPrivacy`** writes the §3 `notificationPrivacy` field through `update()` (missing profile fails natively). The ≤1h deleted-but-tokened residual is handled as a CLASS over two surfaces: direct client writes (rules `exists(users/{uid})` guard on `soloAnswers`; the couple surface fail-closes at detach) and admin-SDK callables (`createInvite` gained a creator-profile-must-exist precondition — a rules guard can never cover a rules-bypassing callable). Logging follows the coach discipline: `logDataRightsEvent` has no uid/coupleId/text fields — deletion events are special-category-adjacent.

- **Device lock (M6.1, ADR-018) — the gate every other flow now sits behind.** `PrivacyGuard` mounts in `MaterialApp.builder`, the ONE point above both `home` and every `Navigator.push` route (the bypass inventory holds: every event-driven navigation in this app is a *pop*, every push is a user tap — so nothing routes around a wrapper there). A deep link arriving while locked still lands in `pendingInviteProvider` (state, not navigation) and renders offstage — captured, invisible, untappable, revealed intact on unlock. **State:** a keepAlive controller seeded SYNCHRONOUSLY from a boot snapshot the entrypoints await before `runHayati` (an async lock check would flash couple content, and the OS would snapshot that flash). Cold start always locks; a background return re-locks past a 60s grace window on `paused`/`hidden` only (never `inactive` — the share sheet, permission dialogs and the biometric prompt itself all pass through it). **Snapshot shield:** an opaque *neutral, brand-free* full-bleed cover on `inactive`/`hidden`/`paused`, closing ADR-017 D3's app-switcher deferral for every surface, not just the coach — brand-free on purpose, since painting the mark in the switcher card would re-identify the app for a user who chose the discreet icon.
- **Daily rollover:** scheduled Function per timezone bucket assigns next unseen question honoring pack/register/seasonal rules; deterministic so client can prefetch offline. *Status: shipped M3.2, seasonal completed S037* (hourly UTC sweep → per-timezone buckets → deterministic selection → create-if-absent `days/{yyyymmdd}`, §3 shape; register honored by construction — the pack IS the register unit via `packConfig`; **seasonal windows resolved per ADR-026** — Hijri via guarded ICU Umm al-Qura, keyed off the dayKey, in-window-unseen-first). The server assignment is **authoritative**: client prefetch is a prediction over the same bundled pack and reconciles to the day doc's `questionId` on sync (an installed app's pack version can lag the deployed Function's). The schedule trigger itself is deploy-verified at the first Blaze deploy.
- **Answer → mutual reveal:** each member answers today's assigned question; the partner's answer is unreadable until one's own exists (server-enforced), then streams in live — both-answered is the revealed, frozen state. *Status: shipped M3.3* (paired home over the §3 read path — stored-zone `coupleDayKey`, honest no-day-yet/pack-lag states; answers subcollection with the reveal `exists()` rule mutation-tested; client mirror never listens pre-ack and maps a denial to locked). **M3.4 closed the loop's production:** `revealedAt` is now stamped server-side by the `answerReveal` trigger (the deliberate M3.3 deferral landed per ADR-012), and the same transaction folds `couples.streak`. The private thread remains parked (M4+ decision) on the same day doc path.
- **Streak & pushes (M3.4, ADR-012):** answer create → `answerReveal` (`onDocumentCreated` on the answers path, `europe-west1`) → ONE serializable transaction: both-answered + unrevealed ⇒ stamp `revealedAt` + apply the pure streak engine (`applyMutualDay`: consecutive increment, one-missed-day grace bridge with weekly ISO refill, gap reset — fast-check property-tested over the parity-fixture zones); duplicate delivery and the two-answers race collapse onto the `revealedAt`-absence latch (exactly one stamp + one streak application, proven in-process by duplicate re-drive, `Promise.all`, AND a forced read-write interleave on a trigger-isolated emulator project). Pushes ride BEHIND the committed transaction, best-effort, through an injectable `MessagingPort` (FCM has no emulator; the send seam is mocked in-process, real delivery = operator item 4): partner-answered nudge (first answer → the partner), reveal push (one per reveal, to the latch-winning invocation's partner — the first answerer in the common sequential case; recipient is best-effort under reordered delivery), and streak-at-risk piggybacked on the hourly rollover sweep at couple-local hour 20 (same single couples read, shared timezone buckets; only non-answerers of an unrevealed day with `streak.count > 0` are pushed). Payload policy is pure and unit-tested: quiet hours 22:00–08:00 couple-local suppress (dropped loudly, never queued), discreet mode defaults ON for AR recipients (PRD F6), and **no payload in any mode ever carries question or answer text** — `composePush` has no such parameter, so the invariant holds by construction. `users.fcmTokens` capture is deferred to the on-device slice: empty tokens are loud counted skips.

**The device-privacy layer (M6.1, ADR-018) — the app's local security posture, and the honest bounds of it.** The threat model is explicit and narrow: *a partner holding the phone* — not a forensic lab. **What it is:** a 6-digit PIN gates the whole app at the root (§4); the credential is stored as `SHA-256(salt ‖ pin)` with a per-device 128-bit `Random.secure()` salt, compared in constant time, in ONE versioned **Keychain** record (`flutter_secure_storage`, `unlocked_this_device` — out of iCloud and device backups). **Keychain, not prefs, is load-bearing:** Firebase Auth persists its session in the Keychain, which survives app deletion + reinstall, while `SharedPreferences` does not — a prefs-resident lock would evaporate on reinstall *while the signed-in session it guards survived*, i.e. a one-gesture bypass. The lock and the session it protects now share fate (so reinstalling does **not** shed the lock — deliberate, and told to the founders on purpose rather than discovered by accident). **There is deliberately NO iterated KDF:** against an attacker holding the extracted record a 10⁶ PIN space falls to any offline search regardless of iteration count, so a KDF here would be theatre; the hash exists only so the raw PIN is never at rest, the *real* at-rest control is the Keychain and the *real* online control is attempt bounding — 4 free attempts, then escalating 30s/1m/5m cooldowns, counter and deadline persisted IN the record (an in-memory counter would mean "unlimited attempts, 5 per relaunch") and the increment persisted *before* the verdict renders, so a kill mid-attempt lands on the consumed side. Failed attempts never destroy data — a wipe-after-N would hand a destruction button to exactly the wrong person. **Biometric is a revocable accelerator, never the credential:** `biometricOnly: true` is pinned by a source-sentinel test (plain `deviceOwnerAuthentication` would accept the *device passcode*, which the phone-holding partner plausibly knows — an app-PIN side door), it is opt-in behind an explicit DV warning, and the platform's opaque biometric-enrollment bytes are captured at enable time and re-checked at every lock-screen mount (`LAContext.domainState.biometry.stateHash` on iOS 18+, the deprecated `evaluatedPolicyDomainState` below it — ADR-018 rev 5 / issue #47; the two representations differ, so an upgrade across iOS 18 revokes once and asks for the PIN, which is the fail-safe direction): **any enrollment change auto-revokes it and demands the PIN**, so a partner who adds their face *after* enable gains nothing. **Discreet mode** = the iOS alternate launcher icon (`setAlternateIconName` over the app's one MethodChannel) — honestly bounded in the UI copy itself: the icon *image* changes, the `CFBundleDisplayName` label under it **cannot** be changed at runtime. **Recorded residuals, none silent:** a holder of the user's identity anchors (SIM for the SMS OTP, or the device Apple ID) can complete same-device re-auth through the forgot-PIN recovery — app-level friction cannot close that, and the honest guarantee is therefore *"casual and silent access is blocked; an identity-anchor holder can force a **destructive and detectable** way in"* (recovery signs the session out and wipes the PIN, so the owner discovers it); device-clock manipulation collapses grace and cooldown *delays* (no persistent monotonic clock survives process death); biometrics enrolled *before* enable are what the DV warning covers; process-memory residue is unscrubbable. KVKK+PDPL export + delete: **shipped M6.2** — the dedicated data-rights paragraph below.

**Slack notifications (S025, ADR-024).** Both workflows end in a terminal **`slack-notify`** job (`needs:` every job, `if: always()`, ubuntu, `timeout-minutes: 5`) that runs the single tested notifier **`tool/ci/slack_notify.sh`** — one source, not the reference repo's four drifting copy-pastes (two of which report the *notifying* job's own name instead of what broke). It exists for one event: **the post-merge `integration-emulator` red**, which by cost design lands on main *after* the session's attention has moved on and today has no reader at all. The notifier is a **side-channel with no vote on the build**, and that guarantee is enforced at two levels — every error path inside the script `exit 0`s, and **`continue-on-error: true`** on the job covers what the script cannot reach (a failed checkout, a dead runner, the job timeout), so a notifier hiccup can never red a green pipeline under rule #7. *All* outcome logic and the noise policy live **inside the script** (success/failure/cancelled derived from `toJson(needs)`; PR successes silent because the session already watches `gh pr checks`; failures never suppressed) — deliberately not in a YAML `if:`, which the shell self-test cannot see and therefore cannot protect. Absent `SLACK_WEBHOOK_URL` (the state the repo ships in until the founder mints one) is a `::notice::` + exit 0 — never a `::warning::` on a green build, which would re-open exactly the annotation noise issue #39 was just closed to remove. The secret is **repository-scoped, NOT `environment: release`** (ADR-024 D4 — `release.yml`'s notifier must be able to report a `sign-upload` that fail-closed *because* that environment is empty; binding it there would be circular). Message content is repo metadata only — **never log excerpts**. The W4 no-silent-retries rule is taken as a **recorded, bounded exception** (ADR-024 D3.1): W4 governs steps producing a *primary* signal, and a missed notification is not a hidden failure; the exception is scoped to this one file. `quality` gained `shellcheck tool/ci/*.sh` + the 14-case self-test (bash/jq/python3, pre-`pub get`), which is what makes every one of those properties *asserted* rather than promised. **Concurrency changed with it (ADR-024 D8):** `ci.yml`'s group now keys **push events on the commit** (`${{ github.workflow }}-${{ github.ref }}-${{ github.event_name == 'push' && github.sha || 'ref' }}`). Ref-keying plus `cancel-in-progress` meant the session's own close commit (§3.4, ~15 min after the merge) **cancelled the main run carrying `integration-emulator`** — and the superseding docs-only run *skips* that job (`code_changed=false`, ci-debt #17), so the merged code's only post-merge verdict was silently destroyed (two of the five main runs before the fix are `cancelled`). PR re-pushes still cancel their predecessor, so the Session-004 billing protection is intact.

**The release lane installs the lock it was given (S080, ADR-056, issue #129).** `release.yml`'s `bundle install` carried a four-clause comment of which **three were false** — the lock was called "documented debt", the dev box was said to have no Ruby so no faithful lock could exist, and bundler was said to resolve fresh. S048 had closed #120 by committing the lock and had corrected the claim in ADR-021 D6 and `fastlane/README.md` while leaving this comment asserting the opposite (addendum 19). The lane now installs **`--frozen`**, so a `Gemfile` edit without a regenerated lock fails loudly instead of being silently re-resolved at release time. **The larger finding was in the thing meant to prevent that:** `gemfile-lock.yml` does install `--frozen`, but it runs `bundle lock` *first*, so it verifies the lock it just regenerated — never the file in the repo, as its own checksum comment concedes. #129 says *"no release run has ever executed with the committed lock"*; **nothing ever had.** So `ci.yml` gained **`gemfile-lock-verify`**, which installs the **committed** lock frozen and runs `fastlane lanes` under it on the same **macos-26 + Ruby 3.3** the release lane uses — same runner deliberately, because a lock is a claim about a *platform* and verifying on ubuntu would exercise the generic `ruby` fallback and prove the wrong thing. It is gated by a job-level `if:` on a computed `ruby_changed` output, so it reads as **`skipped`** rather than vanishing: a paths-filtered workflow is *absent* from the checks list, and absent cannot be told apart from verified — the same Session-002 reasoning that keeps `paths-ignore` out of this repo entirely. ⚠️ **What remains unproven** is the release lane *as a whole* under `--frozen`; only the founder can run it, and the first release after this merges is the confirmation. If it fails at `bundle install`, that is `--frozen` working, and the remedy is to dispatch `gemfile-lock.yml` and commit its artifact.

**A wedged CI suite fails with a name instead of being cancelled in silence (S078, ADR-055, issue #208).** `integration-emulator` was killed at `timeout-minutes: 50` after **38 minutes of complete silence**, parked at `00:00 +0` right after a clean 49-second Xcode build, and GitHub reported the conclusion as **`cancelled`**. The job's own comment named its compensating control and asserted it worked — *"ADR-024's Slack notifier reports the run nobody is watching"* — and for this failure it did not: `slack_notify.sh` sends **nothing** when the outcome is `cancelled`, because a superseded run is not an event (ADR-024 D2, and that policy is correct). **A timed-out job is reported by GitHub as `cancelled`.** So the one control that exists to surface a post-merge red on this main-only job was silent by design for exactly the outcome a timeout produces — the hang was invisible twice, in the log and afterwards. GitHub spends **one word on two unrelated things**, and the notifier cannot separate them from the `needs` results, so the fix is not to teach it a distinction it cannot see: it is to **stop producing `cancelled`** for a case that is not a supersede. `tool/ci/integration_watchdog.sh` bounds each suite *below* the ceiling, so the job ends in **`failure`** with a named suite and reaches Slack through the path that already works; catching the wedge ~34 minutes earlier is the side effect, not the goal. The bounds are **measured, not guessed** — healthy run `32062696199` is 22.7 min = 3.9 setup + 18.6 suites (9.3 of it Xcode), and the first suite carries the cold build at 262.9s against 67–85s for the rest, so it gets 16 min and each later one 6: worst case **44 min inside a 50-minute ceiling that was deliberately NOT raised again** (#208 is explicit that 50 → 60 buys a 60-minute hang). ⚠️ **The load-bearing test is arithmetic, not behavioural:** the watchdog only works if it can fire before the ceiling cancels the job, so `integration_watchdog_test.sh` parses `ci.yml`, derives the suite count from the tree, and fails if the bounds ever sum past `timeout-minutes` — otherwise the mechanism becomes unreachable and the job silently reverts to cancelled-with-no-notification, a dead guard behind green tooling. Three claims in the job's own comments were false and are corrected in place: *"four suites"* (there are **five**), *"the 30-min job timeout is the real bound"* (it is 50), and *"`-r expanded` streams progress so a wedge shows"* (38 minutes of silence is what it produced — it streams between tests, and says nothing while the app is failing to launch). **What this does not do is explain the hang:** the heartbeat, which carries *time since last output* — the quantity that separates "slow" from "wedged" — exists so the next occurrence produces the evidence this one did not.

**The export stops being narrower than the deletion lane (S077, ADR-054, issue #227).** `projectProfile` built the export's profile lane as a whitelist, so `fcmTokens` (one FCM registration token per physical device, ADR-042) and `pushDiagnostic` (the device's own permission report, ADR-049) were silently absent. Meanwhile `deletion-service.ts` step 5 sweeps `users/{A}` **in full** — so the system **deleted data it would not show you**, and "we hold nothing about your devices" was never an available answer, because the deletion lane already conceded we hold it. ADR-049 D7 had kept `pushDiagnostic` out *"for consistency with `fcmTokens`"* and said in its own words that this was *"for consistency rather than for a reason anyone has argued on the merits"*, pinning the omission with a test written to go red at exactly this moment. **The format was decided by a measurement, not a principle:** the export is not a file — `export_screen.dart` delivers it with a single `Clipboard.setData` of the pretty-printed JSON. An FCM token is a **live credential that addresses a phone**, so the raw form would land on the general pasteboard, readable by other apps and, on Apple, relayed to the subject's other devices by Universal Clipboard; the subject would not have to forward it for it to leave the device, and there is nothing they could do with it if they had it. So the two fields are treated **differently, on the merits**: `pushDiagnostic` crosses **verbatim** (no credential — `state` and `detail` are closed enumerations pinned in `firestore.rules` — and it is a statement *about* the subject that we recorded without them ever seeing it, the paradigm Art. 15 case), while `fcmTokens` yields **`registeredDeviceCount` only**, which is the sole non-credential fact a bare `string[]` with no per-token metadata can honestly give. `FORMAT_VERSION` 2 → **3** on the constant's own documented rule. ⚠️ This does **not** wait on **#226** and does not pre-empt it: exporting data the policy does not enumerate *cures* an Art. 15 gap, whereas the reverse order would leave a subject reading that we hold something we refuse to show them — so the lane's wording is mechanical rather than prose, to avoid becoming a fourth statement of what we hold.

**The bidi seam classifies characters itself (S076, ADR-053, issue #137).** `isolateWithin` decided whether to emit `FSI`/`PDI` by asking `intl` for a string's first-strong direction. `intl`'s two character classes are hand-written approximations and it says so at the constant — *"not completely correct according to the Unicode standard… simplified for performance and small code size."* Measured over all 1,114,112 code points: **150** code points it calls strong-**LTR** are strong-**RTL** (the filed issue), **1,783** strong-RTL code points its RTL class never reaches, **322** in its RTL class that are not strong-RTL, **3,308** in its LTR class that are not strong-LTR. **Both classes are loose in both directions**, which is why this replaced them rather than widening one: the seam needs a *three-way* answer — RTL, LTR, or **no direction at all** — and the third was being decided by whichever loose test fired first. A string with no strong character has no direction of its own and must inherit the paragraph's; forcing it to LTR is actively wrong in Arabic chrome. **Two independent defects, and the first fix written addressed only one.** The 150 lie in one stretch, `U+0800–U+08C9`, across **five** blocks (Samaritan, Mandaic, Syriac Supplement, Arabic Extended-B, and Arabic Extended-A *last* of the five, not the whole of it) — that is a range gap. Separately, `intl` matches a **UTF-16 regex**, so an astral character is tested through its surrogates and all **1,024** high surrogates sit inside its LTR class: `Bidi.startsWithLtr` returns **true** for Adlam, for every astral RTL script, and for emoji — **1,632** of the 2,962 strong-RTL code points that exist, more than half. #137's own table records Adlam as matching *neither* class, which is true of the code point and false of the behaviour. Widening ranges does not touch this; **iterating runes instead of code units does**, and a mutant pins it. The classification now reads two **generated** tables (`Bidi_Class R|AL` and `L`) emitted by `tool/gen_bidi_rtl_ranges.py` — 873 ranges nobody can review by eye, so the file is *derived, never edited*, with `--check` and generator self-tests in CI. ⚠️ **The table is pinned to a Unicode version, which is pinned to a *Python* version**, so a runner-image bump makes `--check` fail correctly and confusingly; the tool therefore prints a **different sentence** for "Unicode moved" than for "someone edited the table", because the first is news and the second is a mistake. `intl` is gone from this seam — no hand-written file under `app/lib/` imports it now — though it remains a `pubspec` dependency that Flutter's generated localizations require. **Zero goldens moved**, declared before the run and grounded in a corpus scan: all 894 strings across three ARB files and three content packs classify identically under old and new logic.

**One definition of "raised" (S075, ADR-052, issue #175).** `ElevationTokens.level1` — the plum Level-1 card shadow, ui-ux §9.3, *never black*, which the brandkit assigns to "Cards, sheets" — reached **4** of the app's **14** card surfaces. The other **10** were an inline `BoxDecoration(color: surfaceContainerHighest, borderRadius: cardRadius)` copy-pasted per screen with no shadow at all, separating from the page by a `nightRaised`-vs-`night` step of about **1.3:1** and reading as flat panels of a slightly different colour. **The defect was not ten wrong values but fourteen values**: the eleventh card would have copied whichever neighbour its author was looking at. `raisedCardDecoration(theme, {borderRadius, border})` in `core/design_system/` is now the only one, and `grep surfaceContainerHighest app/lib/features` returns **zero**. It takes a **`ThemeData`, not a `BuildContext`**, because every call site already holds a `theme` and one (`_cardDecoration` in the paired home) is a top-level function with no context — and an optional **`border`**, because `privacy_spotlight_card`/`partner_preview` carry `Border.all(outlineVariant)` over the same surface and the paywall's plan card uses its border as a state signal; either omission would have left the sentinel its first exception, which is how a rule acquires its first hole. **`CardThemeData` is still refused** (ADR-025 D1): constructed `Card(` widgets in `lib/` remain **zero** — and re-measuring that turned up a trap worth recording, since `grep -rn "\bCard(" app/lib` returns **1**, whose single hit is the *comment stating the claim*, so a casual re-measure "corrects" a true claim into a false one. The guard is a **source sentinel**, not a per-screen rendering assertion: "each screen has a shadow" is satisfied by fourteen hand-copied decorations, i.e. by the defect itself. **99 of 360 goldens** were regenerated, and W4's declaration — written before `--update-goldens` — held exactly, including the load-bearing half: the four already-raised surfaces came back **byte-identical**, proving the function reproduces the value they already had. ⚠️ A golden suite is a regression net, not a design review; **nobody has looked at this on a device**, and if the result is wrong the token is wrong, which is a founder call.

**The reveal announces (S074, ADR-051, issue #174).** `RevealChoreography` fired a haptic at beat 2 and nothing else: `grep -rn "liveRegion\|SemanticsService" app/lib` returned **zero hits**, so the product's signature moment — the partner's answer arriving — passed silently for a VoiceOver user, and `RevealPairGroup`'s own doc comment already *claimed* it "announces as one event" (keeping both answers REACHABLE was real; announcing the EVENT was never built). The announcement now rides the haptic's guard rather than growing its own: `_fireRevealHaptic` becomes `_signalReveal`, and every property the announcement needs was **already true there for an independent reason** — at-most-once per State, State re-keyed per dayKey, preserved under reduce-motion (which matters more for the announcement: a user who turned motion off is disproportionately likely to be the one listening), and surviving app resume. Two guards would have been two answers to "has this reveal already happened?", and the failure is not that they disagree today but that a later change teaches one and not the other. It is a **one-shot event, deliberately not `liveRegion: true`** — a live region re-announces whenever its subtree changes, and that subtree holds the streak strip plus an `AnimatedBuilder` rebuilding every frame, i.e. #174's stated worse-than-silence failure reached through the widget's own semantics. `SemanticsService.**sendAnnouncement**(View.of(context), …)`, because plain `announce` is `@Deprecated` after Flutter v3.35.0 and this repo is on 3.44.5 (**the design review caught that; the ADR had named the deprecated one**), gated on the SDK-documented `MediaQuery.supportsAnnounceOf`, with the direction read from the ambient `Directionality` — the one bidi property (ADR-033) no golden can catch, because an announcement is never drawn. The copy says *"is shown"*, not *"is now shown"*: the choreography also runs on cold-open-into-revealed and the source is explicit that no cheap client signal separates that from a live reveal, so a transition claim would be false there — one word, and the sentence is true in both cases. ⚠️ **Android's own accessibility model deprecates announcement events** (disruptive with TalkBack), so M6.5 must revisit the mechanism — recorded now rather than discovered then. **The honest bound:** `flutter test` proves the event is dispatched once, with the right text and direction; that VoiceOver *speaks* it, usefully, needs a device and a person.

**Dependency advisories (S053, ADR-034).** `functions/` carries an advisory check that gates on what a change **INTRODUCES**, not on what the tree contains, and the distinction is the whole decision. `npm audit`'s absolute output moves for reasons **no commit caused** — a third party publishes an advisory against a lockfile nobody touched — so an `--audit-level=high` gate would redden `main` for something no session did and none can fix that hour, which is ADR-024's lesson about guards that cry wolf, transferred. Instead `tool/ci/npm_audit_delta.py` audits the **base and head lockfiles in the same run** against the same registry (`npm audit --package-lock-only`, so no `node_modules` and not even a `package.json` is needed — only the lockfile bytes, which is what makes auditing a historical revision cheap): **a newly-published advisory appears on both sides and cancels**, so the check is *structurally* incapable of firing for a publication event and fails only for an advisory the diff itself brings in. It runs in **`functions-rules`** (a required check) *before* `npm ci`, whose checkout therefore gains `fetch-depth: 0`; threshold **high and above, introduced only**; and it is **fail-closed** — an audit that cannot run exits 2, never 0, because a gate that passes when it could not measure is the `store_metadata` shape (S047) and the shape of #140. It keys on **GHSA id**, not npm's headline: npm emits one entry per affected *package*, so this repo's "12 vulnerabilities" is **two advisories and ten wrappers** — issue #131's own title counted the wrappers. The hermetic self-tests live in `quality` (`tool/ci/npm_audit_delta_test.py`, 14 cases, no npm/network/emulator) and carry the mutation check in both directions. **Which base ref is compared against is policy that lives in the TOOL, not the workflow YAML** (ADR-024 D1: outcome logic a self-test cannot see is unprotected) — the step passes candidates (PR base sha → push `before` → a depth-1 `main`, so a `workflow_dispatch` run is a real check and not a no-op) and the tool takes the first git resolves; when none resolves it emits a `::notice::` and exits 0, the one named hole, which a missing lockfile cannot reach because existence is checked first; the real-npm proof (a seeded `minimist@1.2.0` → exit 1 naming `GHSA-xvch-5gv4-984h`) is recorded in ADR-034. **Deliberately absent:** a committed baseline file (ADR-025 D8's shape — a declaration nothing enforces, and git history is already the baseline), a cron (**GitHub disables scheduled workflows after 60 days without repository activity**, i.e. during exactly the quiet period a scheduled sweep would exist to watch), and Slack routing (the notifier's payload has no field for advisory content and ADR-024 D2's noise policy would suppress it). The half a cron would have covered — an advisory published against an **unchanged** lockfile — has a platform-native answer this repo is not yet using: **Dependabot alerts are DISABLED** on what is a public repo, so they are free, cannot rot, and would watch every ecosystem here (npm, pub, `Gemfile.lock`, Actions) rather than one lockfile. Enabling them changes repo settings and mails a real person, so it is an **operator** action (alerts, not automated security-fix PRs — those would propose the very `firebase-admin@10.3.0` downgrade ADR-034 refuses). Two advisories stand open and **recorded as unreachable** as measured: `brace-expansion` (GHSA-mh99-v99m-4gvg) hangs off a `rimraf` that `google-gax` declares and never imports, and its "available" fix is a mirage — `brace-expansion@5.0.8`'s CJS entry exports an object, so an override breaks `minimatch` at runtime (measured against a passing control); `uuid` (GHSA-w5hq-g745-h8pq) sits under the **optional**, never-loaded `@google-cloud/storage`, only `v4` is ever called, and the advisory is about v3/v5/v6.

**The public site and the invite links (S054, ADR-036/037).** `deploy-site.yml` publishes **ikimiz.beyondkaira.com** from Firebase Hosting, **`workflow_dispatch` only** — publishing is outward-facing and effectively irreversible, so merging to `main` is not consent to publish (`gemfile-lock.yml`'s shape). **Test Information, Beta App Review, and what "the app is with the testers" actually means (S055, ADR-038).** ADR-037's auto-assignment was necessary and not sufficient, and S055 measured the remainder against the live app: build **110** had been `VALID` in TestFlight since 2026-07-27, three beta groups existed at the time (`founders` internal, `arkadaslar` and `Friends` external — **`arkadaslar` was merged into `Friends` and deleted in S057 on founder directive, so the current set is `founders` + `Friends`**), and the *only* gap Apple reported was **four empty `betaAppReviewDetail` contact fields** — the beta description and feedback email were already set. `testflight_testers.py` had called those gaps "founder-owned copy that no session can write for them", which is half true in the expensive direction: the four **facts** are the founder's, the **write** is a PATCH on an API CI already authenticates against. So `--set-review-contact` writes them from **`release`-environment secrets** (`ASC_REVIEW_CONTACT_FIRST_NAME`/`_LAST_NAME`/`_EMAIL`/`_PHONE`) and **never from a `workflow_dispatch` input** — this repository is PUBLIC and dispatch inputs are recorded in world-readable run metadata, so an input box would publish the founder's mobile number permanently. The tool prints field **names** and `set`/`unchanged`/`missing`, never a value, and an `assert_no_leak`-style sentinel test enforces that rather than promising it (ADR-024's precedent). `--submit-for-review` is **dispatch-only**, refuses while `review_readiness()` reports any gap, and de-duplicates by **reading `externalBuildState` before posting** rather than on a status code Apple's behaviour was never measured for. `--status` now prints Apple's **reviewer** (`externalBuildState`/`internalBuildState`, verbatim — the enum is open and only two fail-safe subsets are named in code) and each build's **group membership**, alongside the `processingState` that is only Apple's *encoder*: a build can read `VALID` forever and reach nobody, which is the `store_metadata`/#140 shape met a fourth time. `release.yml` writes the contact on every release and **never submits**; the write is deliberately **non-fatal**, because failing closed there would abort before the assignment step and silently repeal ADR-037's guarantee while `continue-on-error` kept the release green. **The `ikimiz` Hosting site now exists** in `hayatiapp-prod` and the generated site is proven end to end on a preview channel (all six legal pages in three languages, the AASA served as `application/json`, `/i/<code>` rewriting to the invite page); the **live** channel is still empty, because `ikimiz.beyondkaira.com` currently A-records to the founder's own VPS (161.97.172.146, apex-only TLS, HTTP 404) and connecting it to Firebase is a console + registrar step.

**What is DEPLOYED vs what is MERGED (S058, ADR-041, issue #140).** `functions-rules` proves `firestore.rules` against the emulator on every PR — and the emulator loads the **working-tree** file, so it guards a ruleset the runtime never reads. Both projects served the M2.1 ruleset from `d913722` for **eighteen days** while six milestones of rules sat merged and undeployed; every one of those PRs was honestly green, and a founder bug report ("Invite Your Partner shows Something went wrong" — a `permission-denied` on `users/{uid}/soloAnswers/{dayKey}`) found it rather than a gate. **Measured at S058 before designing:** both projects are now in sync (`sha256:0d59af3a5cd72911`, prod ruleset `3702186d` / dev `fbae0b36`, released 2026-07-27T16:16Z), and prod has had exactly **three** rulesets ever — the 07-08 bootstrap, the 07-09 M2.1 one, and the 07-27 remediation — which is #140's narrative confirmed from the platform rather than from the issue. `tool/ci/rules_drift.py` asks `firebaserules.googleapis.com` what is **released** and diffs it against the file on the ref. **There is deliberately no committed `last-deployed.sha` marker to compare against instead:** that is ADR-025 D8's shape — a declaration nothing enforces — and it would fail in the *reassuring* direction, because the lane whose omission **is** the bug is the same lane that would update the marker. Only the authority can answer. Exit codes are a **taxonomy, not a boolean** — `0` match, `1` drift (it looked, they differ), `2` **could not measure** (fail closed: no credential, API error, unreadable ruleset, unexpected shape) — and collapsing 1 into 2 would reintroduce the defect, since a check reporting success when it could not look is precisely what `functions-rules` was doing. The comparison is **byte-exact with no normalization** (a ruleset differing by a trailing space is not the reviewed ruleset), and **coverage is asserted rather than assumed**: a Firestore *named database* gets its own `cloud.firestore/{db}` release, so the tool lists every release and fails **closed** on any second firestore one instead of reporting a partial green — this tool's own failure mode, one level down. Other services (`firebase.storage/…`) are out of contract and are **reported, not failed**; measured S058, both projects have exactly one release each. **Trigger and vote (D2/D5):** the check runs post-merge on **`main` only**, never on `pull_request` — drift is a property of main-vs-the-projects, not of a contributor's diff, and a PR touching Dart going red for last week's undeployed rules is ADR-024/ADR-034's cry-wolf shape reached from a different road — and on **every** main push rather than only rules-touching ones, because the narrower trigger goes green on the next unrelated push while production is still stale. **ADR-034's asymmetry does not transfer**: an advisory is published by a third party, drift is caused by our own omission and is always actionable, which is an argument *for* a vote, and it is taken. **The green-without-measuring hole is closed structurally**: a job-level `if:` cannot read `secrets`, and a job whose every step skipped reports **green**, so the credential probe is its own job (`rules-drift-preflight`) publishing a boolean and `rules-drift` gates on it — either MEASURED (green or red) or **visibly SKIPPED**, with no third outcome, and the skip carries a `::warning::` naming what is unguarded. **That warning is a recorded exception to the notifier rule stated above** (ADR-041 D6.1): an absent `SLACK_WEBHOOK_URL` costs a *notification* and gets a `::notice::`, while an absent `FIREBASE_RULES_VIEWER_SA` means **a gate is not running** and the run's green is worth less than it looks — and because this repo *skips constantly by design*, a skipped job blends in and cannot by itself distinguish "not needed on this push" from "nobody can run it". Bounded and self-clearing: `main` only, and gone the moment the secret exists (#165). `deploy-rules.yml` is the deploy path and is **`workflow_dispatch` only**: `firestore.rules` is the app's authorization boundary, one bad deploy exposes couples' data globally in seconds with no staged rollout, and merging to `main` is not consent to change production's security rules. **Prod additionally requires typing `hayatiapp-prod` into a free-text box with no default** (`testflight-testers.yml`'s group-deletion confirmation shape); dev is a session's to exercise. The lane measures before deploying (a `2` aborts — a blind deploy can overwrite something nobody saw, while a `1` is the normal reason to be running it), deploys, then **reads back**: a vendor reporting success is a claim about its own work, and the guarantee is the release-time re-read (S056's AASA lesson). Credential scope is **split by privilege** (D4): the detector takes `FIREBASE_RULES_VIEWER_SA` (`roles/firebaserules.viewer`, both projects) and requests the `firebase.readonly` scope — **verified against the API's own discovery document**, which lists it for each of the three methods the tool calls (`projects.releases.list/get`, `projects.rulesets.get`) — so the frequently-run automatic job **cannot cause the drift it reports**, while the rare, deliberate deploy lane holds the admin credential. Both are **unset today**, which is why `rules-drift` currently shows as skipped and `deploy-rules` fails closed at its secrets gate; operator items 2(e)(iii)–(iv). **Proven, not asserted:** the detector run against both live projects (in sync, exit 0) and against the **actual M2.1 bytes** from `d913722` (exit 1 with the real diff — if it had existed on 07-10 it would have printed exactly that), and the deploy **command the lane runs** exercised against `hayatiapp-dev` from the local CLI (released, then independently read back as MATCHES; the CLI skipped the upload for identical content and re-pointed the release, which is why `live since` moved while the ruleset id did not). **Neither workflow has itself run** — `rules-drift`'s measuring path and `deploy-rules.yml` are both unarmed until the operator secrets exist, and saying so is the point: ADR-037's auto-assignment "never once ran" for exactly this reason (S056 addendum 69). **Deliberately not built here:** a cron (ADR-034 D4's finding transfers verbatim: GitHub disables scheduled workflows after 60 days of inactivity, i.e. during exactly the quiet period one would exist to watch), and any auto-deploy on merge. ~~A deployed-Functions-code check (a different artifact with no comparable source-identity read — filed separately rather than stretched into this slice)~~ — **filed as #166 and BUILT at S065; the premise that there is "no comparable source-identity read" turned out to be false.** See the next paragraph.

**What is RUNNING vs what is MERGED, for Cloud Functions (S065, ADR-043, issue #166).** The paragraph above was written believing deployed functions expose no source-identity read. They do. `firebase-functions-hash`, the label the CLI stamps on every function it deploys, is **derivable from a checkout** — the derivation was read out of the **installed firebase-tools 15.22.4** rather than out of documentation (`cache/hash.js`, `cache/applyHash.js`, `prepareFunctionsUpload.js`, `fsAsync.js`) and reproduced **all 13 production hashes exactly on the first attempt**, including the two secret-carrying outliers: `endpointHash = sha1(sourceHash + envHash + secretsHash)`, where `sourceHash = sha1(sorted([sha1(bytes) for each packaged file]).join(""))`. **It is a digest over a sorted multiset of per-file digests, not over the zip bytes** — which is the whole reason it is reproducible at all, since a zip carries mtimes and compressor state. `tool/ci/functions_drift.py` emits **two independent verdicts and takes the worse**: a **set comparison** (every name `functions/src/index.ts` exports must be deployed, and nothing else — no hashing, no build; **this is the check whose absence cost S063 the entire push feature**, when `registerPushToken` simply was not there while every check was green) and a **per-function hash comparison**. Same exit taxonomy as `rules_drift.py` — `0` / `1` drift / `2` **could not measure**, never 0 — and three cases resolve to 2 where 1 would be tempting: a function carrying **no hash label** (deployed by `gcloud` or a pre-label CLI: nothing can be concluded, so it is *unmeasurable*, not matching), a listing of **zero functions** while the ref exports some (either maximal drift or a credential that cannot see them — lesson 65, an empty result is *unverified*, not negative), and a **gcfv1 or DataConnect** function (whose source digest takes inputs this tool does not walk). **The reference is a CLEAN tree and the working tree is the diagnosis (D3):** the CLI packages the *directory* and never consults git, and **62 of the 275 files in production's digest are gitignored machine-local debris** (61 under `functions/coverage/`, plus `firestore-debug.log`), so the verdict is computed over `tracked ∪ build output` — what a clean checkout plus `npm ci && npm run build` carries, measured **byte-reproducible across rebuilds**, all 97 files — while the working-tree digest is computed *only* so the report can separate **"production is running code that is not this ref"** from **"production is running this ref, hand-deployed from a dirty tree"**. Both are exit 1; without the split the reader cannot tell an emergency from a housekeeping item. **Reconstruction is bounded and named (D4):** `secretsHash` comes from the deployment's own `secretEnvironmentVariables` because the repo cannot know which secret *version* a past deploy bound — and **secret versions do participate**, confirmed by construction, so a rotation moves the hash with no code change — while `envHash` takes `FIREBASE_CONFIG` verbatim from the deployed environment; consequently **env-var and secret-version drift are explicitly OUT of contract**, and a `functions/.env*` that binds is exit 2 rather than a reimplemented dotenv parser whose subtle bug would read exactly like real drift. **A version pin cannot catch the algorithm moving inside a major**, so the tool additionally **re-verifies four load-bearing shapes against the installed vendor source every run** and refuses if any has moved — the same instinct as `rules_drift.py` reading the CLI's OAuth constants at runtime, but where the silent failure would be worse than a 401: a tool computing confident nonsense and calling production drifted. **Trigger and vote:** `functions-drift-preflight` + `functions-drift`, post-merge on **`main` only**, gated on a boolean so the job is MEASURED or **visibly SKIPPED** with no third outcome, and the skip's `::warning::` **inherits ADR-041 D6.1's exception rather than opening a new one**. It checks **`hayatiapp-prod` only** (D6.2): `revenueCatWebhook` cannot deploy to dev until operator item **0(c)** puts `RC_WEBHOOK_TOKEN` there, so dev is red *by construction* and would redden `main` forever for a filed dependency — and the tempting alternative, a committed expected-missing allowlist, is ADR-025 D8's shape and would absorb a genuinely missing function. Dev is checked by a session on demand with the same command. **Proven, not asserted:** **159 hermetic checks** in `quality` (158 on a tree with `functions/lib` built — the repo-reality section asserts a different half of the contract in each state, because `quality` never builds `functions/` and asserting the built half there would redden for a non-defect), pinned to hashes **measured from production** (a fixture derived from its own subject proves nothing — Google computed these), `js_stringify` checked **differentially against V8** on ten inputs covering control characters, U+2028/9 and astral-plane code points, and **22 mutations each reddening a NAMED assertion**. Run live against both projects: prod diagnosed as a hand-deploy, **dev caught genuinely missing three functions**. **Credential:** `roles/cloudfunctions.viewer` added to the same read-only service account as `rules-drift`, so operator item **2(e)(iv)** arms both — read-only by construction, ADR-041 D4: this tool must never be able to cause the drift it reports. **Built at S070 (ADR-048, issue #206): `deploy-functions.yml`, the last deploy target that was a hand-typed command nothing tracked.** Dispatch-only for `deploy-rules.yml`'s reason — merging to `main` is not consent to change what production *runs* — with the typed `hayatiapp-prod` confirmation, the fail-closed secrets gate, and measure → deploy → **read back**. Three things depart from the rules lane, each argued from a measurement rather than from symmetry. **Prod is additionally pinned to `refs/heads/main`**: a `workflow_dispatch` runs against whatever ref is selected, and deploying a branch to prod would *manufacture* the exact defect this lane exists to remove — `functions-drift` would correctly report production as running source that is not this ref, and the next reader would hunt a drift a dispatch box created on purpose. Dev accepts any ref, deliberately. **The read-back runs `if: always()` and still votes**: a ruleset is one artifact released in one call, while a Functions deploy is **N independent operations** and firebase-tools partially applies *on purpose* (`promptForUnsafeMigration` skips unsafe updates in non-interactive mode and continues), so the most dangerous state the lane can produce — a partially applied deploy nobody measured — exists only *after* a failure, which is exactly when a normal step sequence stops running; the three readings it yields (deploy OK + MATCHES, deploy FAILS + DRIFT, deploy FAILS + MATCHES) are ones the deploy's own exit code cannot give. **`--force` is never passed**: read out of the installed firebase-tools 15.22.4, `promptForFunctionDeletion` returns early when it is set, so `--force` **deletes** any function present in the project and absent from the source with no prompt — a bad barrel edit must not be able to silently remove `revenueCatWebhook` and take the entitlement mirror down; without it the same situation aborts and prints the explicit `functions:delete` commands. The subset selector is **constructed, never forwarded**: `getEndpointFilters` splits `--only` on commas, silently drops any selector missing its own `functions:` prefix, and returns `undefined` — meaning **no filter at all, deploy everything** — when every selector is dropped, so an operator asking for one function is one comma from a full production deploy; the lane regex-validates the names (underscore allowed, hyphen refused because `parseFunctionSelector` splits on `[-.]` into prefix-matched chunks), builds the selector itself, and `functions_drift.py --only` re-validates the same names against the barrel so an unexported name is **exit 2**, never a silent no-op. That flag narrows **both** verdicts and a scoped green says so in the report, the annotation and the success line, while a function **outside** the scope is *recorded but never examined* — parsing first and scoping second would exit 2 over an out-of-scope `gcfv1` or unlabelled function and abort a dispatch that never named it. **`--require-clean-tree`** turns #206's "clean by construction" into an instrument rather than a claim (lesson 92), on the pre-check only — after a *failed* deploy the tree may legitimately carry debris and an exit 2 there would replace the very diagnosis the read-back exists for. It also **closes ADR-043 D9's residual** for anything it deploys: the comparing CLI and the deploying CLI are the same pinned version in the same job, and that agreement is asserted hermetically (every `firebase-tools@` pin under `.github/workflows/` must equal `functions_drift.py`'s `VERIFIED_CLI_VERSION`). **Unarmed until operator 2(e)(iii)**, exactly as `deploy-rules.yml` still is — neither has ever executed — but the command sequence was **exercised end to end against `hayatiapp-dev`** from the local CLI. **Measured before designing, and it corrected the record:** `hayatiapp-prod` now reads **exit 0, MATCHES** over 213 files with **zero** foreign — the 62 gitignored debris files ADR-043 found are gone, because the 2026-08-11T10:51Z redeploy was made from a clean tree and `functions/` has not changed since `52d8065`; the operator page's prediction that the first armed `functions-drift` run would report prod drifted was stale and is corrected.

**All three deploy lanes now agree with each other (S072, ADR-050, issue #223).** The three dispatch-only lanes had three different safety postures, and the ordering was the wrong way round: `deploy-site.yml` (S040) carried neither a ref pin nor `concurrency`, `deploy-rules.yml` (S058) carried neither, and only `deploy-functions.yml` (S070) carried both — **the oldest lane guarded the least and published the most irreversible thing**, because each was reviewed against the state of the art when it was written and nothing ever went back. `gh workflow run deploy-rules.yml --ref some-branch -f project=prod -f confirm_prod=hayatiapp-prod` deployed a branch's authorization boundary to production, and the typed confirmation could not help: **it confirms which project, never which code** — while `rules-drift` on `main` would then correctly report production serving something that is not this ref, sending the next reader after a discrepancy a dispatch box created on purpose. `deploy-site.yml`'s `live` channel is pinned for a **stronger** reason than #223 supposed: what it publishes is the privacy policy and terms that ADR-023 byte-syncs into the app, so a branch publish puts a *third* version into the world — the public page Apple points at, disagreeing with the shipped app — which is ADR-023's sync test routed around rather than through (an `invite_only` live publish carries no legal text, but a branch's `apple-app-site-association` is still what Apple fetches). `preview` and `dev` stay free on every lane, deliberately. All three now declare `concurrency` keyed on the **target-selecting input** with `cancel-in-progress: false` — the load-bearing half, since a deploy killed mid-flight is worse than one that waits — using `github.event.inputs.` rather than the bare context, because workflow-level concurrency is evaluated **before any job starts** and a bad expression there is a *parse* error on someone's first dispatch. **Because two edits would have done nothing about the fourth lane**, `tool/deploy_lane_lint.dart` is a dependency-free source sentinel over a **derived** `deploy-*.yml` glob (an empty derived set is exit 64, never a pass), asserting the concurrency shape, the per-selector group, the ref guard, its **operators** and not merely its operands, both halves in one expression, and that the guard precedes the deploy — with comments stripped first, because every lane now quotes the guard in a header and a lint reading prose would go green on the note left behind when someone deletes it. The design review's blocker was exactly that operator hole: the first implementation matched the four *words*, which also matches `inputs.project != 'prod' && github.ref != 'refs/heads/main'` — dev blocked from a branch, prod through from anywhere, the guard inverted into the hole it closes — and the test now covering it was confirmed red against that form. **13 mutants, each caught by a named check.** ⚠️ **A green lint means the guard is written correctly, never that it was tested:** all three lanes remain unarmed until operator 2(e)(iii) and **none has ever executed** (measured: `gh run list` returns nothing for all three) — though the invite URL answers 200, so the live site was published by hand and the first real dispatch will overwrite it rather than create it.


**The landing and support pages (S059).** Until now `/` served a two-line stub — `<h1>ikimiz</h1>` and one sentence — and **that stub was what `fastlane/metadata/*/support_url.txt` declared as the App Store support URL**. `tool/ci/build_site.py` now renders a real landing page and a real support page from `docs/site/{landing,support}.{tr,en,ar}.md`, on the same generated-not-committed rule as the legal pages (ADR-036: a committed HTML copy would be a third thing to drift). Routes follow the existing scheme — `/`, `/tr`, `/ar` for the landing and `/support`, `/support/tr`, `/support/ar` — which required special-casing `lang_nav` for the landing family, because the naive f-string emits `//tr` for an empty `kind` and a browser reads that as a **protocol-relative URL** and leaves the site. **The decisive design point: both pages are emitted under `--invite-only` too.** The legal pages are blocked behind the founder's unfilled legal name; the support page carries no legal text, is what a confused tester is pointed at, and has no business waiting on a blank in a privacy policy — the two problems were never actually coupled, and are now decoupled by construction with a test that goes red if someone folds them back together. The placeholder gate **does** apply to the site copy and is **not** skipped by `--invite-only` (unlike the legal loop), because these pages ship in that mode and a landing page reading `[COMPANY — TBD]` is exactly as bad as a policy that does. Copy is adapted from `fastlane/metadata/*/description.txt` — the product's already-reviewed store self-description — rather than invented; Arabic is the one page written from scratch and is **flagged for native review**. Two honesty properties are enforced rather than promised: nothing links an App Store the app is not on (extending `test_invite_page_never_offers_a_dead_app_store_button` to the new pages), and the Turkish copy must carry its diacritics — a guard that exists because the first draft was written ASCII-only ("hosgoru gunu") by an author who *guessed* the renderer might not handle UTF-8, when `privacy-policy.tr.md` has carried 53 of them through it since S054. **Two store-vs-app terminology conflicts were found and are the founder's to settle** (recorded on the operator page, not silently resolved): the app says `tohum`/`seed` where the store description says `nar tanesi`/`pomegranate seed`, and the app's `streakMercyUsed` says `Merhamet günü` where the store says `hoşgörü günü`. ## 10. Scalability & cost posture

Firestore fan-out is trivial at our shape (couple-scoped docs, no global feeds — a deliberate consequence of the §Social Layer decision in `prd.md`). Cost ceilings: caps on coach usage are the only meaningful variable cost (M5.1: code-constant defaults behind an injectable seam, Remote-Config-tunable at the deploy era); alerting at $ thresholds via budget alerts. The M5.1 `coachProxy` cost shape (ADR-016): a crisis/help-path call costs ZERO reads and zero provider spend; a persona call is one bounded transaction (4 doc reads, 2 writes) + one provider call, pre-paid by a reserved cap unit — the per-uid 30/min limiter, the 30/day/user cap, and the 1,000/month/couple cap bound worst-case provider spend to ≈$14/couple/month at Sonnet-tier pricing before any key even exists. The M3.2 rollover's cost shape (ADR-011): O(couples) doc reads per hourly sweep plus an O(days-history) projection read per assignment — pennies for years at personal-use scale; the binding fleet-scale constraint is the invocation wall-clock (sequential per-couple reads), with the timezone-indexed sweep query + selection cursor as the documented rework path. The M3.4 additions keep that shape (ADR-012): `answerReveal` fires once per answer create (≤2/couple/day) with an O(1) transaction (4 doc reads + ≤2 writes) plus ≤1 users-doc read per push; the at-risk pass reuses the sweep's single couples read (shared timezone buckets — the sweep is still ONE couples query per hour) and adds one day-doc read per streak-holding couple only in its hour-20-local bucket, once per day. The M4.1 webhook is O(1) per event (ADR-013): ≤3 user-doc reads for identity resolution plus one bounded transaction (1 mirror read, 1 write) — RC event volume is ≤ a handful per couple per month. A `TRANSFER` (M4.3, ADR-015) is bounded by the pre-read gate: ≤20 identity reads (10 per array, after a pure anon-filter/dedupe) and ≤1 transaction per resolving loser (1 in practice); an oversized or unplaceable transfer costs ZERO reads. 100K couples fits comfortably in this architecture; the first real rework (search, community polls aggregation) is a v2 problem and is isolated behind repositories.
