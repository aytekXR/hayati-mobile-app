# Serving ikimiz.beyondkaira.com from the VPS

> **This config was RUN before it was handed over**, not merely written. A local
> nginx 1.24 was pointed at the real vhost's own location blocks (extracted
> verbatim, not retyped) and the built bundle, and every route was fetched.
> Doing that caught two defects that reading the file would not have:
>
> * the app-site-association response carried **`Content-Type` twice**
>   (`application/json; charset=utf-8` *and* `application/json`), because
>   `default_type` and `add_header` were both set — malformed, on the one file
>   whose entire purpose is its content type;
> * every missing page returned **`HTTP/1.1 200 OK`** with the 404 body, the
>   classic nginx soft-404, because the `try_files` fallback named the file
>   instead of `=404`.
>
> Verified after the fixes: `/`, `/tr`, `/ar`, `/support`, `/support/tr`,
> `/support/ar` → 200; AASA → exactly one bare `application/json`; a missing
> path → real `404` with the right body; `/i/<code>` → 200 serving the invite
> page; all three security headers present **on the 404 too**.
>
> A third apparent failure was the *test* being wrong, and is worth recording so
> nobody "fixes" it: `/i/9U4VUVRV` does not contain the code in its HTML. The
> invite page reads it from `location.pathname` into `id="code"` at runtime, so
> the code is client-side by design and its absence from the static body is
> correct.

The site is a **static bundle** generated by `tool/ci/build_site.py`. Nothing
here is committed as HTML (ADR-036: the generator is the single source, and a
committed copy would be a third thing to drift). You build it, you copy it up.

**Why this exists at all:** `ikimiz.beyondkaira.com` already A-records to the
VPS (`161.97.172.146`), the same host as the apex — so serving it from there
needs no DNS change. The alternative (pointing the record at Firebase Hosting)
is operator item 2(e)(i) and remains available; this is the other branch.

## What is broken right now, measured 2026-08-02

```
ikimiz.beyondkaira.com -> 161.97.172.146   (the VPS)
beyondkaira.com        -> 161.97.172.146   (same host)

cert on that host covers:
  ams · bedirhandemirel · beyondkaira.com · brier · matbu · pulse · www · yanki
                                                    ^ ikimiz is NOT among them

https://ikimiz.beyondkaira.com  -> TLS handshake fails (ERR_CERT_COMMON_NAME_INVALID)
http://ikimiz.beyondkaira.com   -> 404 (no vhost defined for that name)
```

So three things are missing and this directory supplies two of them: a
certificate that names `ikimiz`, and a vhost. The third — the files — comes
from the generator.

**The browser will not let anyone click through the warning**, because the apex
sends `Strict-Transport-Security: max-age=31536000; includeSubDomains`. That is
HSTS doing its job. It also means there is no half-working state: until the
certificate is valid, the domain is simply unusable.

## Steps

Run these ON THE VPS unless stated otherwise. Nothing here is reversible by
accident, but step 2 edits a live certificate — read it before pasting.

### 1. Build the bundle (on the dev box, NOT the VPS)

```sh
cd /path/to/hayati
python3 tool/ci/build_site.py --out web/public --invite-only
```

`--invite-only` publishes the landing, support, invite and app-site-association
surfaces and **no legal documents**. Drop the flag once the three blanks in
`docs/legal/` are filled (operator item 2(e)(ii)) and `/privacy` + `/terms` will
be written too. The build REFUSES to publish an unfinished policy, so a full
build fails closed until then — that is the gate working, not an error.

### 2. Add `ikimiz` to the certificate

The existing cert already covers seven names, so **expand it rather than
issuing a second one** — two certs for one nginx means two renewal timers and
one of them will lapse unnoticed. `--cert-name` keeps the existing lineage and
the existing paths, so the vhost's `ssl_certificate` lines stay valid.

```sh
sudo certbot certonly --cert-name beyondkaira.com --expand \
  -d beyondkaira.com -d www.beyondkaira.com -d ams.beyondkaira.com \
  -d bedirhandemirel.beyondkaira.com -d brier.beyondkaira.com \
  -d matbu.beyondkaira.com -d pulse.beyondkaira.com -d yanki.beyondkaira.com \
  -d ikimiz.beyondkaira.com
```

> **Re-derive that name list before running it.** It was read off the live
> certificate on 2026-08-02 and a doc is not the authority:
> ```sh
> openssl s_client -connect beyondkaira.com:443 -servername beyondkaira.com </dev/null 2>/dev/null \
>   | openssl x509 -noout -ext subjectAltName
> ```
> Any name you omit is a name that **stops working** the moment the new cert
> installs. That is the one genuinely dangerous step on this page.

If the vhost is not live yet, certbot's HTTP-01 challenge needs the port-80
`acme-challenge` location from the conf file, so install the vhost (step 3)
first and re-run this.

### 3. Install the vhost

```sh
sudo cp ikimiz.beyondkaira.com.conf /etc/nginx/sites-available/
sudo ln -s /etc/nginx/sites-available/ikimiz.beyondkaira.com.conf \
           /etc/nginx/sites-enabled/
sudo mkdir -p /var/www/ikimiz /var/www/certbot
sudo nginx -t && sudo systemctl reload nginx
```

`nginx -t` before the reload, always: a bad config plus a reload takes down
every other site on the box, not just this one.

### 4. Copy the files up

From the dev box:

```sh
rsync -av --delete web/public/ root@161.97.172.146:/var/www/ikimiz/
```

`--delete` so a page removed from the generator disappears from the server;
without it the VPS accumulates stale routes nobody is testing.

### 5. VERIFY — do not skip, and do not verify by reasoning

The three things that fail silently, each checked directly:

```sh
# clean URLs (Firebase's cleanUrls; nginx does not do this by default)
for p in / /tr /ar /support /support/tr /support/ar; do
  printf '%-16s %s\n' "$p" "$(curl -so /dev/null -w '%{http_code}' https://ikimiz.beyondkaira.com$p)"
done                                   # expect 200 for every one

# the invite rewrite, WITH the code preserved
curl -s https://ikimiz.beyondkaira.com/i/9U4VUVRV | grep -o '9U4VUVRV'

# Apple's file, and its content-type — the header is the whole point
curl -sI https://ikimiz.beyondkaira.com/.well-known/apple-app-site-association \
  | grep -i 'content-type'             # expect application/json

# the certificate now names ikimiz
openssl s_client -connect ikimiz.beyondkaira.com:443 -servername ikimiz.beyondkaira.com \
  </dev/null 2>/dev/null | openssl x509 -noout -ext subjectAltName | grep ikimiz
```

The `.well-known` check is the one to actually run rather than assume. Firebase
needed an explicit `ignore` exception for dot-directories and this repo has
already been bitten by that class once (S056) — nginx has its own version of
the same trap, and a wrong content-type here produces no error anywhere: Apple
just never activates universal links.

## What this does NOT change

- **Invite links still point at `ikimiz.web.app`.** The emitted host is one
  boolean in the app (`kInviteLinkUsesCustomDomain`, ADR-039) and the host set
  is closed. The app already PARSES all three hosts, so nothing already sent
  breaks either way — but until that boolean flips, this domain serves the site
  without being the link target.
- **`deploy-site.yml` still deploys to Firebase Hosting.** It is unaware of the
  VPS. Until that is reconciled, the two can drift, and drift is exactly what
  ADR-036 was written to prevent — so decide which is canonical rather than
  running both indefinitely.
- **The legal pages still do not exist**, here or anywhere, until the founder's
  legal name fills the blanks.
